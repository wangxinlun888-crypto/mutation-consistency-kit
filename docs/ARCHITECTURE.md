# 架构与故障恢复

正确性边界是一份本地 SQLite 数据库。每次公开调用打开自己的连接。请求先写入持久预留记录，再进入业务事务；这样在进程消失后，未完成的请求仍有可查询的身份。

## 持久化结构

| 表 | 保存的事实 | 约束 |
| --- | --- | --- |
| `entries` | 每个目标的当前版本和完整 JSON 正文 | 目标键唯一 |
| `versions` | 从初始化开始的逐版本快照及产生该版本的操作键 | 目标与版本构成主键，每个修改键至多对应一版，初始版为 1 |
| `operations` | 请求键、目标、预期版本、规范化的新内容、持久状态、原因、实际前版及结果版本 | 请求键唯一，成功和失败保存终态，未决预留继续保留 |

业务数据、版本记录以及成功回执全部由同一连接在同一事务中提交。业务拒绝则在该事务内只更新失败回执。数据库标记和格式版本用于识别文件，当前实现支持格式 1。

## 一次修改

1. 将请求内容编码为键有序的 JSON。目标、预期版本和编码后的正文共同确定键的用途。对象成员顺序不影响重放，数组顺序有意义。
2. 获取 SQLite 写锁。若键已存在，核对持久证据以及原请求绑定。未决请求直接返回 `UNKNOWN`，核对完整的终态直接返回原回执。新键写入 `UNKNOWN/reserved` 后独立提交。
3. 仅新预留的创建者继续。获取第二次写锁，核对预留内容和状态，在同一事务快照中核对目标及历史。缺少目标或版本冲突会留下明确的失败回执。
4. 执行带预期版本条件的更新，要求恰好影响一行。追加一条版本历史，保存实际前版与结果版本，然后提交。无论写者来自哪个线程或进程，SQLite 在该库上串行化写事务。
5. 通过独立的读取事务确认回执后返回。若调用者没收到返回值，可以在重启后用同一个键核对。

## 故障与证据

| 分界 | 重开后可见状态 | 行为 |
| --- | --- | --- |
| 预留提交前丢失响应 | 若回执和版本链接均无记录，`recover` 返回 `None` | 仅能证明当前快照查无证据，调用方保留请求并核对 |
| 预留已提交，业务提交前崩溃 | 业务写入回滚，预留仍为 `UNKNOWN/reserved` | 同键同内容再提交也只读回原状态 |
| 业务提交后、响应送达前崩溃 | 当前文档或其后续版本、原版本快照及原成功回执可核对 | 原键恢复出原结果版本，重放无新增版本 |
| 版本冲突已提交 | 失败回执保存当时实际版本 | 日后即使条件变得可满足，旧键仍返回原失败 |
| 数据、历史或回执相互矛盾 | 相关回执返回 `UNKNOWN/inconsistent_evidence` | 拒绝将数据用于交付，保留现场 |
| 获取写锁或存储 I/O 出错 | `replace` 可返回 `UNKNOWN/storage_unconfirmed`，包括预留尚未写入的情形 | 用 `recover` 单独核对；读失败向调用方传播，不转成“查无记录” |

## 版本失效与外部副作用

调用者用 `read` 的文档计算输出，同时保存读取时的目标和版本。交付时 `deliver` 在一个读取快照里重新核对证据和当前版本。版本已经变化就抛出异常。修改即使写入相同值，新请求成功也产生新版本。

这个检查只在线性化的本地读取点有效。它不会发送邮件、执行付款或回调远端。检查返回之后文档仍可能再次改变。业务如果需要跨系统投递，应单独定义投递键、收件方去重及交付结果核对。单库回执只覆盖这里的文档替换；工具对其他数据库和外部服务没有 exactly-once 保证。

## 储存假设与成本

使用支持 SQLite 锁和持久化语义的本地文件系统。写连接设置 `synchronous=FULL` 和外键约束，写事务使用 `BEGIN IMMEDIATE`。每连接锁等待上限为五秒。该值只限制锁等待。只读核对用 SQLite 的 `mode=ro`；发生进程崩溃时，已有文件重开仍依赖 SQLite 自身的日志恢复。

每次核对目标会检查整个目标的版本序列、历史正文格式、当前头和成功回执的双向链接。存储量随历次文档大小增长，核对时间随目标历史增长。恢复可以在当前文档已被合法替换多次后证明某次旧提交。工具没有加密、身份授权、防篡改签名或外部可信锚点。多个相互匹配的记录若被一起删除或改写，单库证据不能证明原历史；文件替换、备份回滚和恶意管理员不属于该证明范围。
